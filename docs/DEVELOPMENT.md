# Development notes

Native menu-bar (macOS) / system-tray (Windows) indicator of AI-assistant usage limits (Rust + Slint 1.13).

## Build / test / run
- Build: `cargo build --release` (`rust-toolchain.toml` pins stable; an older system rustc — e.g. 1.76 — will NOT compile this, so always go through `cargo` in the project dir). On Windows the MSVC toolchain is required — Visual Studio Build Tools with the "Desktop development with C++" workload, or a full Visual Studio install — because that is what the default `x86_64-pc-windows-msvc` target links with; without it `cargo build` fails at the link step, not at compile time. The Windows binary is `target\release\tickover.exe`.
- **`[profile.release]` deliberately keeps unwinding** (no `panic = "abort"`, see Cargo.toml's own comment there): `main.rs`'s `FetchGuard`/`RegistryGuard` turn a panic on a background fetch/install thread into an empty or failed result sent on `drop`, which `"abort"` would skip by ending the process at the panic site instead. The cost is a larger stripped binary — about 8.5 MB on macOS arm64 instead of about 6.8 MB.
- Test: **only under a substituted `HOME`** — otherwise the suite reads and writes the real one:
  ```bash
  REAL_HOME="$HOME"; FH=$(mktemp -d)
  HOME="$FH" CARGO_HOME="$REAL_HOME/.cargo" RUSTUP_HOME="$REAL_HOME/.rustup" cargo test
  ```
  `seed::plugins_dir()` and `config::dir()` take no override, and a few tests read `dirs::home_dir()` directly (`engine_logfile`, `plugin::mod`). This is not a precaution against something hypothetical: a run under the real `HOME` wrote `plugin.copilot.builtin_migrated` into the live `config.json` while the manifests it was seeding went to a temp dir, and that marker — "this install has already had its say about that version" — would have kept the built-in Copilot manifest from ever being delivered, silently. `config::path()` has been sandboxed under `cfg(test)` since; the folder around it has not. `.github/workflows/ci.yml` and `release.yml` run `cargo test` with no substitution of their own, and that is fine there and only there: a GitHub-hosted runner's `HOME` is a fresh, disposable VM home with nothing real underneath it, unlike a laptop running this on the side.
- **`tray-icon` is pinned to `0.22`**, which pins muda 0.17 / objc2 0.6 in turn — that is the set that matches Slint 1.13's winit backend. Upgrading `tray-icon` past `0.22` on its own pulls in a newer objc2 and aborts at startup with a duplicate ObjC class `MudaMenuItem`.
- Headless screenshots: `TICKOVER_SNAPSHOT=/tmp/out.png ./target/release/tickover` (add `TICKOVER_SNAPSHOT_SETTINGS=1` for the settings sheet). Menu-bar pill: `cargo run --release --example widget_probe` → `target/widget-{dark,light}.png`.
- Two example programs support that manual loop: `cargo run --example plugin_probe -- <plugin-id> [--all-surfaces]` fetches one provider end to end through the real auth chain and engine, and prints the result without ever printing a token; `cargo run --example widget_probe` renders the menu-bar pill (light and dark) to PNGs for screenshots.
- Snapshot mode makes one real call to the provider usage API. Don't loop the binary; don't hand-hit the endpoint.
- **Always pass `TICKOVER_DEMO_ACCOUNT=you@example.com` when regenerating anything committed under `docs/`** — it swaps the account label so the shot doesn't publish whichever login the machine happens to hold. The committed images are `docs/screenshot-macos.png` (panel, README), `docs/menubar-widget-{dark,light}.png` (pill, README), and `docs/screenshot-windows.png`.
- Resident instance restart: `pkill -f target/release/tickover; nohup ./target/release/tickover &`. A bundled instance runs from `dist/Tickover.app/Contents/MacOS/tickover` instead, so match the pattern to whichever copy is actually resident — and note that only one runs at a time (single-instance lock beside `config.json`).

## Architecture: providers are plugins (not hardcoded)
No provider is hardcoded. Providers are declarative TOML manifests in `dirs::config_dir()/tickover/plugins/*.toml`, seeded on first run from `plugins/*.toml` — five ship today: `codex`, `claude`, `grok`, `antigravity`, `copilot`. Format + trust model: `docs/PLUGIN-ARCHITECTURE.md`.
- `src/plugin/manifest.rs` — manifest schema + validation (source of truth for the format).
- `src/plugin/engine_logfile.rs` — `engine="log-file"` (glob jsonl, DFS-find `rate_limits` with spelling tolerance, window classification by period length, threshold 720 min). No longer used by a shipped manifest: Codex moved to `http-api` in manifest version 2.0.0. The engine stays — it is a general mechanism any third-party manifest can use — but nothing in the tree exercises it outside tests.
- `src/plugin/throttle.rs` — per-surface request pacing for `http-api`: a floor between requests (below `refresh_secs`, or the scheduled refresh gets skipped), doubling backoff on failure, a stop on 401 lifted by a credential-fingerprint change. Pure state machine, monotonic clock, no sleeping in tests.
- Built-in manifests are seeded once and thereafter upgraded once per shipped version (`plugin::seed::BUILTIN_UPGRADES`, marker `plugin.<id>.builtin_migrated`), and only when the on-disk copy hashes to one previously shipped — an edited manifest is never overwritten.
- **A marker standing at the current version with no file beside it says so in the log** (`main::absent_note`), once per built-in per launch: *"`codex.toml (2.5.1) is not in the plugins folder and this install has already had its say — not putting it back. "Reset plugins" restores every shipped manifest, overwriting edits."* Deleting a delivered manifest is legitimate and the deletion still holds; the line exists because that was the one branch of the seeding cycle with nothing to say, so "why is this provider not in the panel" had no answer anywhere. Two things it is careful about: it speaks of the **file** and not of a provider (`id` is not checked, and whoever renamed a manifest or dropped their own under that name still has a working provider — and the loaded set does not exist yet at that point in startup), and the advice names its own cost, because "Reset plugins" rewrites every shipped manifest, not the one that went missing. In a healthy install it prints nothing.
- `src/plugin/engine_http.rs` — `engine="http-api"` (per-surface auth chain, `{token}`/`{version}`/`{value.<name>}`/`{option.<key>}` substitution in headers, URL and body). Also: `method = "post"` with an optional `body` (Antigravity's `:verb` endpoint is POST-only), `remaining_fraction_path` complemented into the consumed percent a window holds, one `[[windows]]` entry expanded into a row per array element (`for_each`/`for_each_where`/`element_id_path`), and `[[balances]]` for providers that report a calendar period instead of a rolling window.
- `src/plugin/capability.rs` — `CAPABILITIES`, the `requires_reader` gate, and the discipline that pays for it: **every new manifest key is added to its capability's `keys` in the same change** that adds the field, with a negative test and a golden beside it. A wrong spelling there is a backward check that passes exactly the manifest it exists to catch. `tests/manifest_corpus.rs` carries a row per refusal, counted against the `return Err` sites in **both** refusing functions (`manifest::validate` and `capability::check_against`), so a new refusal shipped without a line fails the count. It is a grep and says so: a rule folded into a refusal that already exists raises none — which is why the per-key discipline is a rule and not merely a test.
- `src/plugin/auth.rs` — token sources + `resolve_token`/`host_allowed`. Beyond the file/keychain/env/DPAPI readers: `credentials-map` (pick the one record whose key starts with `key_prefix` — Grok and Copilot key theirs by a string no manifest can spell in advance), `expiry_json_path` (honoured only by `credentials-file`, `keychain` and `win-credential` steps — any other kind is refused at load with a named error; a step that has it resolves **Absent** on a lapsed token so a step behind it can fire, and with nothing behind it the chain reports the token as lapsed rather than merely missing, which becomes the renewal row text and the renewal ping), and `oauth-refresh` (the one step that spends a credential: it exchanges a stored refresh token over the network, enforces `https` and a non-empty `allowed_hosts` itself, caches the result in memory by expiry, and never writes anything back to the provider's own file). Auth chain semantics: each step is Present-ok / Present-err / Absent; stop on first Present. `pub const NO_CREDENTIALS` is the sentinel `readings()` matches to hide an absent surface — keep main.rs's filter using that const, not a literal.
- `src/model.rs` — universal `ProviderReading`/`Window`; every consumer (popup, pill, title, auto-ping) goes through it.
- `main.rs` is provider-agnostic except the "toggle bridge": some settings/tray checkboxes still key off well-known ids `codex`/`claude` (config keys unchanged for backward compat).

## Behaviour worth knowing before changing it
Each of these looks simplifiable at a glance; the reason it isn't is in the same line.
- Menu-bar title label rule is asymmetric: the lowest-`order` plugin's label is dropped only when it's the sole visible row (`bare_when_sole`); tests assert byte-exact strings (`"96/80"`, `"Cx …·Cl …"`, `"Cl 55/30"`, `"Limits"`).
- Auto-ping fires on a **state**, not an edge: the PRIMARY window is *empty* (`used_percent` absent or 0) and `plugin.<id>.pinged_at` is older than that window's start (`main.rs::ping_due`) — so a machine asleep at the reset pings when it wakes, and one ping per window is enforced by the timestamp, not by a window id. A NaN counts as busy. The weekly window and the desktop surface never arm the *window* ping. A second, independent trigger fires the same command for a manifest whose `[ping]` sets `renews_token`: a surface whose auth chain declares a token expiry finding that token lapsed or refused (`main.rs::renewal_ping_due`/`classify_renewal_across_surfaces`), gated by the same ten-minute floor and offered at most once per distinct token per surface. An edge rule (fire within 120s of the reset) would miss a machine asleep at the reset; the state check does not. Specification: `docs/PLUGIN-ARCHITECTURE.md`, "Ping".
- `CODEX_HOME` means `$CODEX_HOME/sessions` for the `log-file` engine — expressed declaratively via `[logfile] root_env` + `root_env_join="sessions"`, not by hardcoding. The shipped Codex manifest no longer uses that engine; the rule and its tests stay for any manifest that does.
- Claude's token JSON path is read with 4-form tolerance: `claudeAiOauth.accessToken|claudeAiOauth.access_token|accessToken|access_token`. Different Claude Code CLI versions have written the token under each of these keys, and narrowing the list would blind the plugin to an account still authenticated by an older client.
- Keychain item-not-found resolves to Absent, which hides the surface; access-denied surfaces an inline error instead. Collapsing the two into one outcome would hide a permission problem the user can actually fix behind the same blank space as "never logged in".
- opt-in surfaces (Claude desktop): `readings()` filters out readings of currently-inactive opt-in surfaces even if cached, so turning the checkbox off hides the row immediately and a fetch already in flight when it's turned off can't resurface it.
- **The bar tooltip is drawn by the window, not by the bar** (`BarTip` in `ui/widgets.slint`). Slint has no z-index — painting order *is* declaration order — so a bubble declared inside a bar is painted before every row below it and comes out with the next window's caption written across it, and it is inside `providers-region`'s clip as well, which cuts whatever hangs past the fold. `LimitBlock` therefore only reports hover; the one bubble is the last child of `card`, after the rows and the settings sheet and outside the clip. Moving it back next to the bar it describes is the obvious-looking change that reintroduces both bugs. Two consequences to keep: a leave event is honoured only from the bar that raised the bubble (a fast drag delivers the next bar's enter before the last one's leave), and `present_popover` clears it (dismissing the panel under the pointer sends no leave at all). Still open: a row destroyed while hovered — hysteresis flipping it to `not-started` removes the touch area, a reconcile rebuild destroys the instance — sends no leave either, and the key is positional, so the stale bubble can end up over a different bar. The fix is to surface `Window.key` into `WindowData` and key the tooltip by it.
- **Dock mode places the window once, and only a status-item click moves it after that** (`popover_moves`). A dock-mode window is draggable, so re-placing it on every show would discard where the user put it; a tray click is the one presentation that names a place. The flyout (non-dock) is placed every time. The decision is a pure function beside `panel_target_visibility` for the same reason — neither branch is reachable through a real window in a test.

## Plugin settings UI
The settings sheet is a generic plugin manager: per-plugin enable, plus toggles the plugin declares. Two toggle types are built in (`[ping]` auto-ping, opt-in `[[surface]]`); a plugin can also declare `[[option]]` bool toggles (key/label/default). All toggle state lives in `config.json` keyed by plugin id (`plugin.<id>.enabled|ping|surface.<sid>|option.<key>`), with the codex/claude ping/desktop toggles bridged onto the legacy `auto_ping_*`/`monitor_desktop` keys for back-compat. `[[option]]` values are handed to the engines as `{option.<key>}` → `"true"`/`"false"` substitution (same mechanism as `{token}`/`{version}`), applied to http headers/URL (incl. `[account].url`) and log-file glob/root. Add/Edit/Remove/Open-folder use native macOS dialogs (osascript) — all interpolated strings go through `applescript_escape`. `remove_plugin_keys` clears `plugin.<id>.*` on delete. The sheet scrolls (Flickable, pinned header/footer, ~540px cap) so any plugin count fits.

- **plugin `id` is a filename** (`<id>.toml`) — `validate()` restricts it to `^[A-Za-z0-9_-]+$`, and add-plugin re-checks canonical containment (`plugin_manifest_target`) + writes with `create_new`. This closes path traversal via a hostile/careless imported manifest id. Don't loosen it.
- **Tests must NOT touch the real `~/Library/Application Support/tickover/config.json`** — config path is injectable via a `#[cfg(test)]` thread-local (`with_test_config_path`); the resident app runs against the real file, so a test writing it would corrupt live settings. Any new config test uses the helper. Forgetting it is no longer silent damage: with no override set, `config::path()` under `cfg(test)` resolves a throwaway per-thread file rather than the real one. The **neighbours** of that file are still un-sandboxed — `platform`'s `instance.lock` and `show-panel` hang off `config::dir()`, and `seed::plugins_dir()` lives in the library while `config` is a module of the binary, so one sandbox cannot cover both. Hence the substituted `HOME` above, still.
- **Seeding happens only at first launch and on Reset plugins** — `load_plugins`/reload paths read the folder without reseeding, so deleting the last plugin does not resurrect codex/claude.
- Auto-ping is gated by both plugin-enabled and the ping toggle, re-checked on the tick that runs the ping command — a state, not an edge fired once after a delay; the window-model reconcile (`reconcile_window_model`) reuses the inner `Rc<VecModel>` so a bar's hover and glide survive the 1s tick. What it reuses on is the whole **sequence of `Window.key`s** being unchanged — not per-key matching, so a reorder or a partial change rebuilds the model rather than shuffling rows inside it. Equal row *counts* was the old test and is a different question: one window appearing as another vanishes keeps the count and shifts every later index, so each row gets overwritten with a different window's figures under the caption it already had.

## Plugin registry
Manual "Check updates" pulls a single `index.toml` from `DEFAULT_REGISTRY_URL` (`src/main.rs`), diffs installed plugins against it, and offers install/update. Core is `src/plugin/registry.rs` (index schema, sha256, hand-rolled SemVer with pre-release ordering, `diff_installed` state machine, `analyze_trust`, lockfile). Network is two functions, `fetch_text` and `fetch_bytes`; everything else is pure/tested (no network in tests). Manifests carry an optional top-level `version` (`#[serde(default)]`).
- The registry itself lives **in this repository**, at `plugins/index.toml`, fetched raw off `main`; it lists the five shipped manifests beside it (`plugins/*.toml`). Editing a shipped manifest without bumping its `index.toml` entry (`version` *and* `sha256`) breaks the download for everyone reading the sha256 against stale bytes — `tests/registry_index.rs` fails the build over exactly that.
- **Install/update:** download manifest via `fetch_bytes` (raw bytes, 10 MB cap **before** buffering — not `fetch_text`, whose UTF-8 round-trip would break the hash); verify sha256 over those exact bytes *before* parsing; reject if downloaded `manifest.id != clicked entry.id`; write the **raw bytes** (never a re-serialized manifest — pristine-detect hashes the on-disk file); install = `create_new` under `plugin_manifest_target` containment, update = write `<name>.toml.tmp` then atomic `rename` targeting the **clicked** id (never the downloaded manifest's id — else a hostile manifest could overwrite another plugin's file). sha mismatch / id mismatch ⇒ nothing written.
- **Lockfile** `registry-state.json` lives beside `config.json` (outside `plugins/` so `load_dir`/seeding never sweep it); records origin url/version/sha256 per id for provenance + local-edit detection. Cleared on remove.
- **Registry trust gate fires on any of four things, not one ANDed pair:** `analyze_trust` asks for confirmation when (1) a store-backed auth step — a credentials file or map, the Keychain, Electron Safe Storage, the Windows Credential Manager, or an OAuth refresh, but not a plain `env` step — sits behind `engine = "http-api"`; (2) the manifest declares a `[ping]` command; (3) `local_files` is non-empty — an auth step's own credential file, an `oauth-refresh` client-discovery file/bin/pattern, a `[[http.value]]`/`[http.version]` file, a `jwt-file` account lookup's token file, or a `log-file` manifest's own `root`/`glob` read scope; or (4) `credential_sources` is non-empty — an `env`/keychain/Credential-Manager/Electron-Safe-Storage step naming its own specific source. Only (1) is narrowed to `http-api`; (2)–(4) fire whatever the engine is, so a `log-file` manifest whose one auth step reads an environment variable asks exactly as loudly as an `http-api` one that reads and sends it on. There's still no host condition. Any registry-installed (or manually imported) plugin that trips the gate prompts a native confirmation (`untrusted_hosts` highlighted; two osascript passes on macOS, one message box carrying the full disclosure on Windows); bundled manifests are seeded, never installed, so they bypass it. sha256 is transport integrity only, not provenance — signing is a named future gap.

## Trust model (security)
A plugin manifest is user/third-party editable and declares BOTH where a secret is read (credentials-file/keychain/env/electron-safe-storage) AND where it's sent. `allowed_hosts` + `redirects(0)` protect a *trusted* manifest from typos/open-redirects; they are NOT a sandbox against a hostile author. Installing a manifest = trusting it (like a crate/extension). Provenance controls (signing) beyond the current sha256 integrity + disclosure are future hardening — the approval gate for a store-backed http-api manifest already ships (see the registry trust gate above). Bundled manifests (`plugins/*.toml`) are the trusted defaults.

## Windows code
Built and run on Windows 11 (x86_64, MSVC), so every `#[cfg(windows)]` arm compiles against a real toolchain and the binary has actually launched there — but they are not all *exercised* equally: `CredRead` and the DPAPI desktop-token path compile and are reached, with nothing on that machine for either to find (the CLI token came from `~/.claude/.credentials.json`, the step before them in the chain).
- **Dialogs are per-platform, and both halves must stay fail-closed.** `show_alert` / `confirm_remove_plugin` / `pick_toml_file` / `show_trust_dialog` each have a macOS `osascript` arm and a Windows `MessageBoxW`/`GetOpenFileNameW` arm; anything that is not an explicit approval — a dialog that could not be shown, a closed window, a cancel — is "no". `MB_TOPMOST` is required (the popover is always-on-top and would cover the dialog blocking its own UI thread), `MB_DEFBUTTON2` keeps Return off a destructive default, and `OFN_NOCHANGEDIR` keeps the picker from moving the process's working directory. The trust dialog has no "Show Details" pass there — a message box gets Windows' buttons — so Windows shows the full disclosure in one.
- **`take_snapshot` does not work.** It returns a fully transparent buffer for a correctly drawn window on both renderers, and aborts inside femtovg's `imgref` (`stride > 0`) roughly one run in ten. `TICKOVER_SNAPSHOT` therefore does not call it on Windows; screenshots are screen captures.
- **The popover hangs off whichever side of the status item has room** (`popover_origin`), because the taskbar is at the bottom. Do not reintroduce an unconditional "below the anchor".
- **A tray click arrives after the focus-loss hide it caused** (`tray_click_dismissed_panel`). Reading `is_visible()` alone makes the item open-only.
- **The tray indicator is a badge, not a pill** (`menubar::render_badge`), drawn at `SM_CXSMICON` rather than resampled, with the figures in the tooltip — Windows has no title beside a notification icon.
- **Both parsers strip a BOM** (`plugin::strip_bom`). "Edit" opens a manifest in Notepad, whose Save has historically written one; an unparsable config reads as empty and the next write erases every setting.

## Claude surfaces

`claude.toml` declares two `[[surface]]` entries, `cli` and `desktop`, each with its own credential chain; the general contract is in `docs/PLUGIN-ARCHITECTURE.md`.

| Surface | Token store | macOS | Windows |
|---|---|---|---|
| **CLI / VS Code** | `~/.claude/.credentials.json` / Keychain `Claude Code-credentials` / Cred Manager (in that order) | works | works (credentials file) |
| **Desktop app** | `<config>/Claude/config.json` → `oauth:tokenCacheV2` (Electron Safe Storage) | needs a one-time Keychain **Allow** for `Claude Safe Storage` | DPAPI, compiles and runs; no desktop install here to read |

- **CLI/macOS** works end-to-end.
- **Desktop/macOS**: the desktop app locks its Safe-Storage key to itself, so the
  first read shows a system Keychain prompt — click **Always Allow** and the
  account populates. Until then that section reads "allow Keychain access…".
- **CLI/Windows** reads the credentials file, which is the first step of the
  chain and the one a `claude` login writes; the Credential Manager step after
  it compiles and runs but had no item to find on the machine this was checked
  on. The DPAPI desktop path is in the same position: built and reached, with
  no Claude desktop install there to decrypt.

Accounts appear automatically: any Claude login found gets its own section. A
window's tick/countdown uses assumed window lengths (5 h; weekly). Note the
"weekly" bucket is reported as `seven_day` but in practice resets sooner.
